## What this round was worth

The change is a new CI gate, the threat-model re-read the gate protects, and the Alpha 7
baseline. Before review, all five script gates were green, 14 tests passed, and the gate had
been mutation-tested five ways by hand against the document it reads.

The review did not run the gate. It read it. Three real checks turned out to be able to stop
checking without anything failing.

### 1. An unreadable number silently disabled the arithmetic check (high)

`parse_summary` returned `None` for a stated total it could not read, and `check` skipped the
comparison when the total was `None`:

```python
    if total is not None and total != len(row_ids):
```

The parser understood `"Fifty-five threats."` through a hardcoded word table. Measured against
the real document:

| Rewording | Parsed total | Problems reported |
| --- | --- | --- |
| `Ninety-five threats.` | `None` | 0 |
| `Fifty threats.` | `None` | 0 |
| `fifty-five threats.` | `None` | 0 |
| `Fifty-six threats.` | `56` | 1 |

Three of four rewordings disabled the check. A gate that treats "I do not understand this" as
"nothing to report" is worse than no gate, because the green tick is believed. An unreadable
total and a missing total sentence are now both errors.

### 2. A row with an invented status was reported as the wrong problem (medium)

`parse_threats` skipped any four-cell `TH-` row whose status cell named no legend status. That
skip is how the parser separates threat rows from other four-cell tables, but it made an
invented status indistinguishable from a deleted row. The only complaint left was:

```
TH-17 is in a summary bucket but has no threat row
```

That message points at the summary. The actual error was in the status cell. On the occasion
this matters, the row is right and the status word is wrong — so a maintainer following the
message would edit the wrong table. `rows_without_a_known_status` now names the status:

```
TH-17 has status '**Basically fine**', which is not one of 'Mitigated', ...;
the summary counts key on those exact strings
```

I checked that no existing four-cell row in the document would be newly rejected, rather than
assuming it: no row with a `TH-` first cell lacks a recognised status.

### 3. My own fix for finding 2 did not exist (high)

The first attempt added a `statuses_seen` dict inside `parse_threats`, populated it, and returned
nothing. `check` had already been wired to call `rows_without_a_known_status`, which did not yet
exist — so the code would have raised `NameError`, but the dict itself was pure dead weight that
read as a working check.

This is the highest-value finding of the round precisely because no test would have caught the
dict: it would have been committed as code that looks like a status check and is not. It was
caught by reading the diff back before committing, not by any gate, which is the honest
description of how it was caught.

### 4. The tests could not have found any of these (medium)

None of the 14 original tests would fail if the total check were deleted. Every mutation I had
run by hand changed the *document*, so the checks fired; none changed the *checker*, so a check
that was never installed stayed invisible. Four tests were added that assert the gate rejects an
unreadable total, a missing total, and an invented status, and that the real document has no
row with an unknown status.
