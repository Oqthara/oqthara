## What this round was worth

A7.4 looked like a one-command change and took a full session, because the interesting question was
never "how do I generate the file" but "how do I know the file is doing anything". Three separate
approaches reported success against a deliberately corrupted checksum before one of them proved
verification was on. The findings below are mostly about that gap — between a control existing and a
control being exercised.

### 1. The metadata file was not the control, and three checks said it was (high)

`./gradlew --write-verification-metadata sha256 …` produced a plausible file. To check it was
enforced, the slf4j-nop checksum was corrupted to `0`×64 and the build run. It passed.

That "pass" is what the rest of this record is about. Three approaches were tried before one
observed the failure:

| Attempt | Result | Why it proved nothing |
| --- | --- | --- |
| `./gradlew dependencies --configuration runtimeClasspath` | `BUILD SUCCESSFUL` | Resolves module metadata, never fetches artifact bytes |
| `./gradlew build --rerun-tasks` | `BUILD SUCCESSFUL` | Re-executes tasks but reuses cached artifacts unverified |
| `:oq-stdlib:classes` against the `runtimeOnly` coordinate | `BUILD SUCCESSFUL` | `runtimeOnly` does not resolve during `classes` |

`./gradlew :oq-cli:standaloneJar --refresh-dependencies` failed correctly:
`Dependency verification failed for configuration ':oq-cli:runtimeClasspath'`, `2 artifacts failed
verification`, `BUILD FAILED in 3s`.

The design conclusion, which is the actual deliverable: `./gradlew build` verifies only what it
*downloads*. On a warm cache it resolves nothing, so **deleting the metadata file leaves every build
green** — and CI is warm after its first run. A metadata file with no forcing step is a control that
appears in review and runs nowhere. Hence the two pieces: a CI step that forces a re-download, and a
static checker for the deleted-file case where Gradle has no failure to raise.

### 2. The first generated metadata file was incomplete (medium)

The first `--write-verification-metadata` run produced a file that failed the very next resolved
build:

```
One artifact failed verification: junit-bom-5.12.2.module (org.junit:junit-bom:5.12.2)
```

`junit-bom-5.12.2.pom` was present; `junit-bom-5.12.2.module` was not. The generating invocation had
not forced every descriptor to be fetched. Regenerated against `:oq-cli:standaloneJar
:oq-cli:testClasses --refresh-dependencies`, the file grew to 44 components, and a clean
`--refresh-dependencies` build then passed.

This matters beyond this commit: it means "the generator succeeded" is not evidence the file is
complete, and the file only reveals the gap when something resolves what it covers. Anyone
regenerating must follow the generator with a clean forced build, exactly as the commit does.

### 3. Two tests asserted the exemption table's membership, including a row this change retires (medium)

`test_check_threat_model.py:94` and `test_check_risk_register.py:205` each asserted
`gradle/verification-metadata.xml` was in the document's "citations that intentionally do not
resolve" table. Creating the file correctly retired that row from both documents, and both tests
then failed — **against correct documents**. This is the same defect the repository has now hit
repeatedly: a test that restates the document's contents is a second copy of the document, and the
copies drift. It is the hardcoded-count failure wearing different clothes.

Both were rewritten to assert invariants — the table parses, every row states a reason — and the
"every exempted path genuinely does not exist" loop is left to the companion test and to the checker
itself.

**The first rewrite attempt was itself wrong and was caught by mutation testing.** An earlier version
of the risk-register test added an assertion that no exempted path exists, computed with
`(SCRIPTS.parent / path).exists()`. That fails on `conformance/`, a directory that legitimately
exists and is exempted because it is cited for its contents. The test was removed rather than
adjusted; the companion test already covers existence using the checker's own `resolve_citation`,
which handles the directory-citation case correctly.

Both rewritten tests were then re-mutated, because a rewrite that no longer targets the real code is
indistinguishable from a passing test:

| Mutation | Expected failure | Observed |
| --- | --- | --- |
| `parse_exemptions` returns `{}` | table not found | `the exemption table was not found in the real document` |
| a row's reason blanked | reason missing | `site/versions.json is exempted with no reason` |
| `resolve_citation` returns relative paths regardless of existence | exempted path resolves | `site/versions.json is exempted as absent but resolves` |

A first mutation attempt inserted `return {}` at the wrong occurrence of `for line in block.splitlines():`
— the string appears twice in `check-risk-register.py`, and the edit landed in `parse_summary`. The
mutation appeared to pass. It was caught by checking `grep -n` rather than trusting the harness, and
this is the second time in this session that a mutation silently hit the wrong target. Mutation
harnesses need to prove their own edit landed.

### 4. R-008 bundled two risks and was narrowed, not closed (low)

R-008 read "No dependency verification and no action pinning by digest". Closing half of it required
saying so explicitly, or the count would have suggested more progress than occurred. The row and body
now cover action pinning only, with a paragraph stating that the dependency-verification half moved to
TH-44 / A7.4 and why. A7.5 remains open and still counted.

### 5. One transient test failure, observed once, unexplained (low)

`FAILED (failures=1)` appeared in the baseline run at the start of a mutation harness. It could not be
reproduced in 30+ subsequent runs — 5 normal, 20 looped, 5 with `-B`, plus runs from a different
working directory — with the file confirmed byte-identical and grep-verified free of any mutation.
The honest record is "observed once, not reproducible, cause unknown". It is written down here rather
than dropped because a test suite that fails once in thirty runs is a real property, even if this
session could not characterise it. The final state of the suite is `Ran 283 tests ... OK (skipped=1)`,
re-run after every remaining edit.

## A process note about this session

Mid-way through updating the threat model, an edit whose `old_str` spanned a heading matched the
wrong instance and truncated several sections; the file has eight `### Residual risk` headings. It
was detected by reading the region back, recovered with `git checkout --` (which reverted *all*
uncommitted work on that file), and every change was then reapplied one at a time with the diff
inspected after each. The final diff was audited line by line: all 23 deletions in that file are
intentional. Recorded because the recovery was only possible by noticing, and the notice came from
reading the file back rather than from a green check.

## What the round did not do

It did not enable signature verification. `verify-signatures` is `false`: checksums prove the bytes
match a previously recorded value, not that they came from the upstream project. Closing that needs a
trusted-key list per dependency and is out of scope for A7.4.

It did not verify the *correctness* of the pinned checksums by an independent channel. They were
recorded from a download over TLS by Gradle and are trust-on-first-use — which is what the threat
entry now says instead of implying provenance.

It did not make the CI forcing step cover every configuration. It covers `runtimeClasspath` for
`oq-cli`, which holds both pinned coordinates; a stale-checksum failure in a configuration that is
neither in `standaloneJar` nor `testClasses` would still be caught only by a cold-cache developer
build. `testClasses` is included in the generating invocation to widen this, but the generating set
and the CI-verified set are not identical, and that asymmetry is not closed here.

It did not pin actions by SHA. That is A7.5, and R-008 stays `Open` for it.
