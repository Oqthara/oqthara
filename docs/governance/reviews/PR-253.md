## What this round was worth

The change under review is a security fix, so the review's job was to attack the fix rather than
re-read it. Three of the eight findings are in the fix itself, and two of those were found after
the commit that claimed to have closed the finding — which is the honest shape of this work and the
reason the second commit exists.

### 1. The fix restated its own guarantee too broadly (high)

ADR-0068 claims cost is bounded by pattern length times name length. That was true of the matching
loop and false of parsing, because `expandClass` materialised every range member. A 360-character
pattern of Unicode-spanning classes therefore needed gigabytes before a single name was compared.
The amplification had not been removed; it had moved from the backtracking engine into the parser,
and the ADR written to describe the removal asserted the property that was violated.

Found by suspicion, not by the fuzzer: the numbers in the Javadoc did not match the code path that
built the token list. That is worth stating plainly, because the fuzz targets were green at the
time and would have stayed green — a single wide class is too small to matter under a 2 GB heap.

### 2. A regression test had stopped running, and the count went down without anyone noticing (high)

The `@Test` above `aPatternFullOfStarsIsMatchedInLinearTime` was consumed when a new case was
inserted above it. The suite still ran 31 tests and still passed. Nothing in the repository compares
the number of test methods to the number of annotations, so the only reason this was caught is that
the diff was read line by line and the annotation above an unrelated method looked wrong.

The guard added in `89dcd72` closes the class of defect for this file. It is a local fix to a
repository-wide exposure, and the exposure remains in every other test class.

### 3. The first fuzz target for the defect could not have caught it (medium)

`globClassesMatchTheirOwnMembers` was written, registered, and run for 3,894 executions against the
expanding mutation — and passed. The target was doing exactly what it said and the defect needed a
product of terms to become visible, which a single generated class never produces.

This is recorded rather than quietly repaired because it is the failure mode that makes coverage
numbers misleading: a target that exercises the code and cannot fail looks identical, in a report,
to one that protects it. The corrected version fails in 58 runs against the same mutation.

## What was deliberately not done

- The ReDoS sanitizer is **not** suppressed anywhere. The finding that started this work was a true
  positive, so suppressing it would have hidden the class of defect the work was about. The target
  runs with it enabled.
- `Patterns.glob`'s directory walk remains unfuzzed; the targets call `matchesText`, so traversal is
  covered only by `GlobTest`. This is named in `docs/spec/fuzzing.md`'s gap list.
- The `@Test`/method count guard was added to `GlobTest` only. Extending it to every test class is
  the right follow-up and is not in this change.
