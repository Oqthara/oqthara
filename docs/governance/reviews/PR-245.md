## What this round was worth

Two real defects, both in the same direction — the change overclaimed safety it does not provide,
which is the precise failure mode it was written to correct.

### 1. The new sentence repeated an overclaim the language spec disavows (high)

The first draft closed with:

> Choose `oq run`, with its budgets, for anything you do not trust.

`docs/spec/language.md` says the opposite in the paragraph directly above its own reference to
`backend.md`:

> Oqthara is **not** a sandbox. A program that is allowed to run can read the files the user can
> read, start the processes the user can start, and reach the network the user can reach. The
> limits above prevent accidental exhaustion; they do not contain hostile code.

A change whose whole purpose is to stop the specification implying a containment guarantee was
ending with a containment recommendation. `oq run` does enforce a 50,000,000-step budget and
host-call deadlines, so the advice is not empty — but "anything you do not trust" claims hostile
containment, which is exactly what those limits do not provide. A reader who followed it would
conclude that running untrusted code through `oq run` is safe.

Rewritten to state what the budgets bound and to point at `SECURITY.md` for the rest:

> If you want the step budget and host-call deadlines that `oq run` enforces, run the program with
> `oq run` rather than building a jar. Those limits bound accidental exhaustion; they do not
> contain hostile code, on either backend. Oqthara is not a sandbox.

### 2. The launcher half of the test did not assert its exit status (low)

Every sibling test in the class asserts `assertEquals(0, launcher.exit(), launcher.err())` before
reading the output. The new test checked only the output text. `build` printing `codepath:
interpreter launcher` and then exiting non-zero would have passed — and the two codepath lines
are printed at different stages, so that is not a hypothetical pairing.

## A finding that was not real, and how it was caught

a one-sided test — that I wrote from memory of drafting rather than from the diff. Reading
`git diff` showed the paragraph had never contained the sentence I claimed to have fixed, and the
test had contained both halves from its first commit.

The record was deleted and rewritten. Recording invented findings is worse than recording none:
the review gate counts them, the category table totals them, and the audit trail then documents
work that did not happen. The two findings above were each reproduced against the tree before
being written down.

## Checks run against the change's own claims

- The three escapes named in the paragraph are the three TH-15 measured, whose probe output is
  quoted in the threat model rather than restated from memory.
- `9 tests, 0 failures` was read from the surefire XML (`tests="9" failures="0" errors="0"`), not
  from a Gradle task that exits 0 whatever the suite does.
- The test was mutation-checked by inverting its compiled-codepath assertion: `9 tests completed,
  1 failed`, then restored. It asserts the measured behaviour rather than passing either way.
- The `read` refusal string asserted in the test, `is not compiled yet`, is the same string the
  threat model quotes, so a change to it fails a test rather than silently dating the prose.

## What the round did not do

It did not test a program that uses `use` *and* `read` together, where the refusal order decides
the jar shape. A reader could still misread which came first; the paragraph is written not to
depend on the order, but that combination was not executed.

It did not re-measure that a compiled jar's runaway loop completes without the step budget. That is
TH-07, already `Accepted` and measured in an earlier segment; this change cites it rather than
redoing it, and says so.
