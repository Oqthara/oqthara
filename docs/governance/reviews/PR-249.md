## What this round was worth

The item looked like transcription: port fifty lines of shell into PowerShell and mirror the tests.
It was not. The defect that mattered was one missing `-Force`, and the reason it mattered is that a
`try`/`catch` written to detect a *missing* asset also caught a *broken read* and reported the same
benign answer.

### 1. A swallowed exception turned every signed release into "unsigned" (high)

The bundle is downloaded to `.oq.jar.sigstore.json.$PID`. Dotfile. `Test-Path` finds it;
`Get-Item -LiteralPath` refuses it without `-Force` and throws. The read of `.Length` therefore threw
into:

```powershell
} catch {
    $hasBundle = $false
}
```

`$hasBundle` stayed `$false`, so control reached `has no published signature, only a SHA-256` on
every signed release, and `cosign` was never invoked. On a machine without `cosign` — the common
case, and the one the warning branch is written for — the output is indistinguishable from a release
that genuinely is not signed. The regression would have shipped on the note that Windows parity was
achieved.

Six new cases failed on the first honest run. The fix is `-Force` plus a comment naming why it is
load-bearing:

```
$hasBundle = ((Test-Path -LiteralPath $bundle) -and ((Get-Item -LiteralPath $bundle -Force).Length -gt 0))
```

Proven by reverting it: `not ok 14 ... cosign was never called`, `not ok 15 ... a tampered jar was
accepted`, `not ok 18 ... wrong message`. 17 passing, 3 failing.

The general lesson, and it is the third instance of it across Alpha 7: **the audit question for a
`catch` is not "what does this handle?" but "what else can reach it, and does the default flatter the
code?"** Here the default turned a verification into a shrug.

### 2. The end-to-end tests had never run off Windows (high)

The block invoked the installer through `Start-Process -WindowStyle Hidden`. `-WindowStyle` is
Windows-only, so on macOS and Linux the cmdlet threw before a single case executed, and the block
failed in a way that reads like a missing HTTP server. Ten cases — the whole end-to-end half,
including three that predate this PR — had only ever run in the Windows CI job.

That matters less for the tests than for what it implies about the *product* path: the same class of
platform-only parameter in `install.ps1` would have been invisible from this host. It now branches on
`$IsWindows`, and the local run exercises the shared logic.

### 3. `$isWindows` is not a legal variable name here (medium)

The first branch variable was `$isWindows`. PowerShell variable names are case-insensitive, so this
collides with the read-only automatic `$IsWindows` and the script dies with `Cannot overwrite variable
IsWindows because it is read-only or constant`. Renamed to `$onWin`.

Cheap to hit, cheap to fix, and only visible by running the file — which is the argument for running
it.

### 4. The tampered-jar case was vacuous before it was written (medium)

The first version called `New-Fixture`, which writes the jar, then re-wrote the jar with "tampered"
content. The signature stub compares a hash recorded in the bundle against the jar's real hash, so
the test only means something if the bundle records the *pre-tamper* hash and the jar on disk is
different. It now: builds a good fixture, reads the signed hash, writes a bundle recording it,
overwrites the jar **and** rewrites its `.sha256` to match, so only the signature can notice. A
positive-control case asserts the same stub accepts an untampered jar, so the negative case cannot
pass by the stub failing at everything.

This is the same failure mode as A7.5's gate: a test that would pass with the feature deleted.

### 5. Two warning branches, one wording, checked literally (medium)

The POSIX installer's wording is a contract that users have already seen. The PowerShell branch
reproduces it — "detects corruption and NOT tampering" — and the tests assert on the distinguishing
phrase rather than on exit status alone, because exit status alone cannot tell "warned and
continued" from "verified".

`OQ_REQUIRE_SIGNATURE=1` is asserted in both the no-cosign and no-bundle branches. That is four
distinct outcomes, and each has a case.

### 6. `OQ_COSIGN` is a seam that could become a hole (low)

Honouring an environment variable as the cosign path means a hostile environment can point at
anything. That is not a new exposure — `OQ_JAVA`, `OQ_RELEASE_API` and `OQ_RELEASE_TAG_BASE` already
work this way — but it is worth stating plainly: **an attacker who controls the environment already
controls the installer's inputs**, and `OQ_REQUIRE_SIGNATURE` with a real `cosign` on PATH is the
posture to test against. Documented in the header beside the existing seams rather than treated as a
guarantee.

### 7. The cleanup was in `finally`, the verification was not (low)

The bundle's temp file is removed in `finally` so a failed verify does not leave a stale bundle to be
mistaken for the next run's. Checked that `Fail` throws rather than exiting the process, so `finally`
actually runs — a `Fail` implemented as `exit` would leak the dotfile into `$installDir`.

Confirmed by reading `Fail`: it `throw`s, and the case at line 19 asserts the failure message
surfaces through `Invoke-FixtureInstall`'s `Threw`/`Message` pair, which only works if the throw
propagated.

## Not claimed

- The Windows-only branches (the `.cmd` cosign stub, the `.cmd` launcher rewrite) are exercised by the
  `windows-latest / installer tests` job, not by the macOS run above. CI is the authority for them.
- Authenticity remains opt-in. With no `cosign` installed, neither installer verifies anything; both
  say so. That is the recorded residual in R-020, not something this PR changes.
- Neither installer script is itself signed. Authenticode for `install.ps1` remains an open
  hardening idea, noted in R-020's residual and out of scope here.

## Verdict

No blocking findings. The change is a faithful port plus the two defects the port exposed, and both
defects are pinned by tests that fail when reverted.
