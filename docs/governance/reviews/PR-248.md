## What this round was worth

The interesting part of A7.5 was not pinning thirteen lines — that is mechanical. It was that the
acceptance named two files, three hold write scope, and the check meant to keep the property true
had no test that could fail. The findings below are about the margin between "the rule is written
down" and "the rule is enforced".

### 1. The acceptance named two files; three hold write scope (high)

`codeql.yml` declares `security-events: write` — it uploads analysis results — and it was not in the
acceptance's list. A literal implementation would have pinned `release.yml` and
`site-content-dispatch.yml`, certified the property, and left five mutable tags in a workflow with a
write permission. Those tags are `github/codeql-action/init|autobuild|analyze@v4` and `checkout` and
`setup-java`.

The gate therefore derives scope from declarations rather than from a filename list, and its first
run found the gap:

```
action pins: 3 of 6 workflows hold write scope and are pinned: codeql.yml (declares security-events:
write); release.yml (declares contents: write); site-content-dispatch.yml (references
secrets.SITE_DISPATCH_TOKEN)
```

This is the same shape as the count problems this repository keeps hitting: a list of files is a
second copy of a property, and the copies drift. `codeql.yml` was pinned rather than exempted.

### 2. An annotated tag's ref points at a tag object, not a commit (high)

The obvious implementation of "resolve the tag" is `git ls-remote` or the refs API, taking the first
SHA. For three of the seven actions that SHA is **not** a commit. `gradle/actions@v6`,
`softprops/action-gh-release@v3` and `github/codeql-action@v4` are annotated tags: the reference
names a tag object, whose `object.sha` is `7ca78c1…`, `40c2ca6…` and a CodeQL tag object
respectively, each with `"type": "tag"`. Pinning that value names something that is not a commit and
would not resolve as a step.

Each was dereferenced through `git/tags/<sha>` and the resulting commit's message checked against the
tag before being written down:

| Action | Tag object's dereferenced commit | Version |
| --- | --- | --- |
| `gradle/actions/setup-gradle` | `8da46b539cd8fe6ab27ca75128919a18d757604c` | v6 |
| `softprops/action-gh-release` | `8a0cd651e5b2365bd640854a3fa5dfc70e4875f3` | 3.0.4 |
| `github/codeql-action/*` | `33d7b85da1a04171e211befe2c739303b9a4c066` | 4.39.3 |

A naive resolution would have produced three broken pins that no test here would have caught, because
a 40-hex string is indistinguishable from a 40-hex commit without asking what it names.

### 3. The threat-model gate reported agreement about a document that disagreed with itself (high)

This was found while updating TH-45, and is the most consequential finding in this record because it
is a defect in a *gate*, not in a document.

TH-45's row was changed to `Mitigated`. The summary table at the end of the document was not edited,
so it still counted the threat under `Not mitigated` and stated `Mitigated | 16`. The gate reported:

```
threat model: 55 rows, 17 + 12 + 14 + 12 = 55, summary and buckets agree
```

Exit code 0. The printed `17` came from counting the per-threat status column, not from the summary
table, and `check()` compared only: each summary row's stated count against the number of ids it
listed, that the buckets partition, that every row is in some bucket, and that the total matches.
None of those compares a threat's **row status** with the **bucket listing it**. A stale bucket is
internally consistent with itself and satisfies all of them.

Reproduced against the real document before changing anything:

```
TH-45 row status : Mitigated
TH-45 in bucket  : Not mitigated
gate problems    : []
row-vs-bucket mismatches the gate does NOT report: [('TH-45', 'Mitigated', 'Not mitigated')]
```

The gate now rejects that, and it rejected the stale table the moment the fix landed:

```
threat model: TH-45 is listed under 'Not mitigated' in the summary but its row says 'Mitigated';
the two must be the same status
```

Fixing the gate first is deliberate: fixing the document first would have produced a green gate and
left the hole.

### 4. The new gate test only isolates the fix when the mutation is count-neutral (medium)

The first version of `test_an_id_listed_under_the_wrong_status_is_rejected` moved one threat from
`Not mitigated` into `Mitigated`. Run against the *pre-fix* gate it failed — but for the wrong reason:
removing one id changes that row's stated count, so the existing count check rejected it. The test
would have passed for a gate that had never gained the cross-check.

It was rewritten as a **swap**, exchanging the first id in each of two buckets. Both stated counts,
the partition and the total are then unchanged, so only the row-versus-bucket check can notice:

```
$ # pre-fix gate
Ran 19 tests in 0.042s
FAILED (failures=1)
$ # fixed gate
Ran 19 tests in 0.040s
OK
```

This is the session's recurring lesson in a new costume. A test that fails for a reason other than
the one it names is a check that is not checking — the same defect as `dependencies` passing against
a corrupted checksum.

### 5. Five mutations, all caught (medium)

`scripts/check-action-pins.py` was mutated five ways with the file restored after each:

| Mutation | Result |
| --- | --- |
| accept any ref as a pin | FAILED (failures=4) |
| scope detection returns nothing | FAILED (failures=5) |
| a missing version comment is tolerated | FAILED (failures=1) |
| `check_workflow` returns `[]` | FAILED (failures=5) |
| `WRITE_SCOPE` never matches | FAILED (failures=6) |

The fifth is the one that matters for the design: breaking the scope regex fails six tests, because
`TheRealWorkflowsArePinned` names the three files **explicitly**. Deriving the expected set from the
same helper the gate uses would have let the tests agree with a gate that checked nothing.

### 6. Bare filenames were cited twice, and rejected by both gates (low)

Writing R-008's replacement cited `release.yml`, `site-content-dispatch.yml` and `codeql.yml` as bare
filenames in running prose. `scripts/check-risk-register.py` rejected all three:

```
- release.yml is cited but does not resolve from the repository root or from docs/governance/, and
  it is not listed under 'Citations that intentionally do not resolve'
```

The same mistake had already been made six times against the threat model in this session. Both
checkers require a repository-relative path, which is correct — a bare filename resolves against
nothing and reads as verified.

### 7. A path was split across a line break (low)

In the same paragraph, `.github/` ended one line and `workflows/ci.yml` began the next, producing a
citation that is a filename in the source text and a broken path in the rendered document. It passed
only because each half resolved as a separate token. Fixed by rewrapping; the region was read back to
confirm.

### 8. A drafting artifact was written into a shipped document and removed (low)

While updating A7.5, a paragraph reading "Wait — sixteen is wrong; the table sums to thirteen.
Corrected below." and a duplicate table were inserted into `alpha-7-security-baseline.md`. Both were
noticing-in-public: correct for a scratchpad, wrong for a governance record. Removed and replaced by
the single correct table, verified by `grep -c` that the counts are 6 + 2 + 5 = 13. Recorded because
it was caught by re-reading the section, not by any check.

## What the round did not do

It did not configure Dependabot to bump the pins. They will age, and a stale pin is a stale
dependency. That trade is written into both the baseline item and R-008's residual section rather
than left to be discovered, and a `dependabot.yml` change is the obvious next item.

It did not verify the pins' *provenance* by an independent channel. Each SHA was resolved from the
GitHub API and its commit message compared to the tag; that establishes the tag pointed there when
this was written, not that the author of that commit is trustworthy.

It did not extend the rule to read-only workflows. `ci.yml`, `docker.yml` and `nightly.yml` keep
major-version tags, as the acceptance permits. That is a deliberate stated exception, and a test
fails if one of them gains write scope — so the exemption is enforced from the moment it would
matter rather than by inspection.
