## Findings

Eleven findings were consolidated from one round: two critical, three high, three medium, three
low. All eleven are applied.

The two critical findings and three of the high ones shared a single root cause, and it was not
the one the first investigation proposed. The initial hypothesis was that the interpreter's
`hasLocal` gate was wrong and should walk the chain. Reading the code disproved it: `Ast.Var` and
`evaluateCall` both consult `Env.hasLocal`, which is `values.containsKey`, so the interpreter is
self-consistent — a `use` name bound only in an enclosing scope does *not* hide the class, and the
class wins in a nested block. The defect was that `Lowering` walked the whole chain while the
interpreter asks only the current frame, so the compiler hid the class where the interpreter did
not. The fix is in the analysis alone; no interpreter change was made, because none was needed.

## What the round confirmed

- `Env.hasLocal` is `values.containsKey` and does not walk parents; `Ast.Var` and `evaluateCall`
  both consult it before `javaTypes`, so the interpreter's rule is "current frame hides the
  class, an enclosing scope does not". That is the rule the lowering now mirrors.
- `Interpreter.hoist` binds `fun`, `data`, `class` and `contract` into the frame `executeBlock`
  was handed, before any statement runs, which is why a `fun` collision is a current-scope
  binding and `localScopes`' statement-order record could not see it.
- `executeBlock` adds no frame of its own, so `If` and `While` bodies get one fresh frame while
  `ForEach`, `ForRange` and the `catch` handler share the frame that already holds their name.
- A refusal must be emitted before anything that can throw, or the true reason is masked. This
  is why refusing a nested `use` before resolving its path also fixes finding 6: the two
  requirements point the same way.
- All nine reproducers reproduce on `ffabcb8` and agree on `57b8b94`.

## Mutation testing

Each mutation was applied to `Lowering.java`, `:oq-cli:test --tests '*BytecodeCompilerTest'` was
run, and the file was restored from a copy. Before the fix, all four of these passed, which is
what finding 11 is about.

| Mutation | Before the fix | After the fix |
| --- | --- | --- |
| `seededBlock(loop.body(), loop.name())` → `block(loop.body())` | 0 of 105 failed | 1 of 112 failed — `aLoopVariableShadowsTheUsedClassName` |
| `inCurrentScope` → `boundSomewhere` in the used-class gate | 0 of 105 failed | 2 of 112 failed |
| `seededBlock` → `block` for the `catch` handler | 0 of 105 failed | 1 of 112 failed — `aCaughtErrorNameShadowsTheUsedClassName` |
| `hoistedScopes.push(hoisted)` → an empty set | 0 of 105 failed | 1 of 112 failed — `aFunNamedLikeAUsedClassHidesTheClassName` |

The first mutation reproduced the original symptom exactly: `expected: <1\n2>` but
`was: <class java.lang.Math\nclass java.lang.Math>`. The second broke both the outer-assignment
asymmetry (`expected: <5\nclass java.lang.Math>` but `was: <5\n5>`) and the `fun` collision
(`expected: <0>` but `was: <1>`).
