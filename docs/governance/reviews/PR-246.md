## What this round was worth

The change itself is small and the Docker behaviour is verified in CI. The findings are all about
the *evidence* rather than the control: two of the three are checks or claims that would have
passed while proving nothing, which is the defect class this repository has now hit four times.

### 1. The jar-writability step passed when the jar was missing (medium)

The step added in `dcd6b90` was:

```yaml
if docker run --rm --entrypoint sh oqthara/oq:ci -c 'echo x >> /app/oq.jar'; then
  echo "::error::/app/oq.jar is writable by the container user; TH-46 is open"
  exit 1
fi
echo "/app/oq.jar is not writable, as intended"
```

It asserts that the write did not succeed. A missing jar, a broken image and a typo in the path all
produce a non-zero exit too, and every one of them would have printed "`/app/oq.jar` is not
writable, as intended". A container whose jar had been deleted would pass the step that exists to
prove the jar cannot be replaced.

This is the same shape as the threat-model gate's "a total the parser could not read was silently
skipped": a check that treats "the expected thing did not happen, for any reason" as success.
Finding it in a shell `if` rather than a Python parser is the reason it is worth writing down — the
defect is in the assumption, not the language.

Fixed in `6046216`: the jar is checked to exist and be non-empty with `test -s` first, and the
write attempt must yield a *permission denial* specifically.

```yaml
docker run --rm --entrypoint test oqthara/oq:ci -s /app/oq.jar
output=$(docker run --rm --entrypoint sh oqthara/oq:ci \
           -c 'echo x >> /app/oq.jar' 2>&1 || true)
if ! grep -qi "permission denied" <<<"$output"; then
  echo "::error::expected a permission denial writing /app/oq.jar, got: $output"
  exit 1
fi
```

Simulated all four outcomes before committing: `Permission denied` passes;
`No such file or directory`, a broken command, and `Read-only file system` each fail.

### 2. Four gate tests encoded the document's counts instead of reading them (medium)

Moving TH-46 between statuses changed the summary from `14 + 15` to `15 + 14` and broke four tests
in `test_check_threat_model.py`. The document was correct; the tests were wrong.

They failed because each spelled its target out literally:

```python
text.replace("| **Mitigated** | 14 |", "| **Mitigated** | 15 |", 1)
text.replace("| **Not mitigated** | 15 | TH-09, TH-10,", "| **Not mitigated** | 15 | TH-10,", 1)
```

A hardcoded count in a test is a second copy of the document, and the two drift — the exact
anti-pattern the test file's own docstring warns about ("a test that constructs its input from the
same constant the checker uses"). The counts had simply been typed by hand rather than imported,
which is not different in effect.

They now locate the row by status through a `bucket_line` helper and derive the count and the IDs
from that row, so a future bucket move is a no-op for the tests. Re-mutation-tested after the
rewrite: disabling the stated-count comparison, the no-bucket check and the overlap check each
fails a test, so the rewrite did not turn three tests into tautologies.

The first attempt at the two-bucket test was itself wrong — it replaced the first ID in the
"Not mitigated" row with an ID already in that row, producing `TH-09, TH-09` rather than a
cross-bucket duplicate. The test failed and was corrected before this record was written.

### 3. The baseline said "done" while the entry said the item was third (low)

`A7.3` was marked `**State:** done` with a "What was done" note, but the paragraph immediately below
still read "**Why third:** … It is third because it needs a working Docker daemon to verify". Both
statements are about the same item in different tenses and a reader has to reconcile them.

"Why third" records the ordering rationale at planning time, which is still true and still useful.
Left in place deliberately rather than rewritten: deleting it would remove the reason the item was
sequenced where it was, which is the part that stays true. Noting it here because it was a
candidate for "contradictory documentation" and was decided not to be one.

## What the round did not do

It did not build the image locally. `docker info` fails on this machine, so the container evidence
is entirely the CI run. That is stated in the pull request body rather than glossed.

It did not verify that a program running *as* `oq` inside the container cannot escalate. It can
write inside `/work` and read what that user can read; the mitigation is scoped to replacing the
interpreter, and the threat entry now says so instead of implying containment.

It did not test the case where `/work` is a bind mount owned by a different uid than 1001. The
workflow mounts `examples/` (`drwxr-xr-x`), which works because the files are world-readable. A
user mounting a directory they cannot read would get a permission error from `oq`, which is the
same behaviour any non-root process has — not a regression, but not exercised either.
