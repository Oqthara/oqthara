## Findings

Two rounds were run. Both reviewers were told to break the change rather than approve it, and
both read the diff instead of the commit message.

The first round cleared the production fix and found that the documentation around it was wrong
in three ways and that the second embedded program had no test. The second round found something
worse: the paragraph the first round's fixes added to ADR-0048 quoted a user-facing error message
that exists nowhere in the code. It had been assembled from a fake JVM's own echo inside the test
file and attributed to production — a document claiming behaviour the code does not have, which
is precisely the defect this pull request exists to record.

## What was examined

The first reviewer read `git diff origin/main...HEAD` and, rather than reading the claim that the
program runs, ran it: `oq build` then `java -jar`, confirming `[1,2,3]` and `10` from the fixed
program on both backends. It swept 204 builtin names to confirm nothing else in the repository
carries the same defect, checked that `sort` and `json_write` are absent from `HOST_DEPENDENT`
so they are compiled-safe, and confirmed every `DATABASE` builtin exists at the arity used. It
also established why the *test* layer is correct even though the documentation was not: `OqRunner`
is interpreter-only, and the interpreter is the production path, so `theLanguageCheckIsAProgramThatRuns`
tests the same layer the installer uses.

The second reviewer tried six mutations of the database program against the new guard and found
three that pass, which is the residual in finding 9. It ran the built jar to confirm the exact
stdout `[{"n": 7}]` including the space after the colon, checked that `@TempDir` leaves no
`compat-check.db`, `-wal` or `-shm` behind across the eleven tests, and confirmed the extracted
programs are byte-identical to `origin/main` except for the two renamed builtins. It recomputed
214 independently, and reproduced the count-checker holes by probe: a misspelled class and a
number word both exited 0 while dropping `checked` from sixteen to fifteen.

Both reviewers were told to say which claims they could verify and which they could not, and the
second round was run precisely because the first round's fixes had introduced a new defect.

Commands run: `python3 -m unittest discover -s scripts/tests -p 'test_*.py'` (198 tests, OK),
`python3 scripts/check-docs-sync.py` (exit 0), `./gradlew clean build --no-daemon
--console=plain --rerun-tasks` (BUILD SUCCESSFUL, 1621 tests), and the reported failure itself:
`java -jar oq.jar runtime install` in an empty `HOME`, which installs and then reports
`managed runtime: … (Java 21)`.

## What this record is not

It is not a claim that the change is free of defects, and finding 9 is the part that is not
fixed. It records two adversarial rounds by reviewers sharing the implementer's model, which is
why `**Independent:**` says `no`.

The second round is also the reason this file says what it says. A reviewer that shares the
implementer's model still caught a fabricated error message that the implementer had just written
into the ADR, because it checked the string against the code instead of reading it. That is the
narrow thing this mechanism does well, and it is not the same thing as the review being
independent.
