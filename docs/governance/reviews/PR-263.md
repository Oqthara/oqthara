## What this round was worth

Three of the eight findings were caught by running the artefact rather than by reading it, and one
was caught only because a claim in a *different* file forced a recount.

The sharpest is finding 1. `c9_precedence` looked correct: the comparator was right, the arity
refusal was right, the expected messages matched, and the harness reported `ok`. The defect was that
the line carrying the probe's meaning could not change. A reversed two-element list `[3, 1]` is still
`[3, 1]`, so the same output would have appeared if the builtin had refused *and* Java had then run
the sort anyway — the precise scenario the probe exists to exclude. Everything about the probe was
green except its ability to fail, which is the one property no self-consistency check can see. The
fix was two characters of fixture and a corrected sentence, and the reason it was found at all is
that a comment claimed the line proved something and the claim read as too strong to leave alone.

Finding 3 is the one that says most about this document set. Correcting a count by hand is the act
the inventory warns about, and the same edit silently rewrote an adjacent sentence about an
experiment into a claim about a number of probes that experiment never saw. The available repair was
to soften the sentence; the honest one was to run the experiment. It took a twenty-line harness, both
directions, and about a minute. That is a low price for not writing an untested measurement into a
governance record, and the fact that softening felt like the natural move is the thing worth noticing.

Finding 5 is a repeat of a pattern this repository has now recorded three times. Grepping for the
*number* finds the places that quote a count; grepping for the *claim* finds the places that depend on
it, and the second set is where the reader actually goes wrong. The GUI paragraph did not contain a
stale `19` — it contained a stale `C1–C8 only` and an inference built on top of it.

## Not verified

- **C11.1 has no probe and this branch does not give it one.** Row C11.1 is a class on the user's own
  classpath. `run.py` invokes `java -jar`, which ignores both `CLASSPATH` and the working directory,
  so there is no way to hand a probe an extra entry. The three mechanisms were tried and only
  `java -cp "<dir>:<jar>" <mainclass>` works, which is a different invocation shape. A probe that
  resolved `Hello` from the harness's own classpath would prove the opposite of the claim, so the gap
  is stated in the inventory and in the probe header. Closing it needs a runner change — an
  `EXTRA_JVM_FLAGS` map keyed by probe name, or a committed fixture jar — and that is a deliberate
  decision this branch did not take.
- **The five probes were checked against the current jar only.** They pin present behaviour on both
  backends. They do not establish that the behaviour was correct at any earlier revision, and nothing
  here bisects a regression.
- **`c12_unrestricted` asserts reachability, not safety.** It prints `0` and `true` and says nothing
  about whether that authority should exist. The row's classification is the inventory's, and this
  branch neither re-derives nor endorses it beyond confirming the documented doors are open.
- **`alpha-6-requirement-matrix.md` and `alpha-6-conformance-fallback-accounting.md` still quote
  `19`.** Neither was edited. They are dated point-in-time records of the Alpha 6 measurement, opened
  by an explicit "Measured:" line, and this branch judged that correcting a historical measurement to
  today's number would misrepresent what Alpha 6 found. The Alpha 7 report is different — it is
  present-tense and was corrected. This is a judgement, not a verified fact, and a reader who wants
  those two files brought forward can ask for it.
- **No gate re-derives the report's claims.** This branch hand-corrected three instances of one stale
  claim. Nothing will notice the fourth instance added by a later merge, and that gap is now named by
  PR-260 finding 4, PR-261 finding 5 and PR-262 finding 5 without being closed by any of them.
