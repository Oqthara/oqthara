# Runtime provenance and signing — decision brief

**State:** OPEN — awaiting a maintainer decision. No part of D3 is implemented.
**Scope:** [ADR-0048](../../adr/0048-runtime-manager.md) D3 (provenance) and the signing item
named in its status line.
**Blocks:** nothing already merged. D1, D2, D4, D5, D6, D7, D8 and D9 are implemented and do
not depend on the choice below.

This brief exists because D3 cannot be built without a decision the maintainer has not yet
made, and building it against a guess would produce a real security control that protects an
artefact nobody publishes. It states the decision, the options, and what each costs. It does
not choose.

## What D3 requires

A runtime archive is accepted only when its SHA-256 matches a value **compiled into `oq`** for
that specific archive, and the download happens over TLS. The distinction matters: a checksum
fetched from beside the archive detects corruption, not substitution, because whoever can
replace the archive can replace the checksum. A digest in the binary is not fetched at install
time, so an attacker who controls the network and the mirror still fails.

**Consequence: the digests must exist before the code that checks them can be written.** This
is a build-pipeline decision, not a coding decision, which is why it is blocked on the
maintainer rather than on implementation effort.

## What exists today

- `release.yml` builds the CLI jar, writes `oq.jar.sha256` beside it, verifies the checksum in a
  fresh directory, and uploads both. That checksum protects a download of *Oqthara*, not of a
  *JDK*.
- Nothing in the repository publishes, mirrors or pins a JDK archive. The installers extract an
  archive the user already has and refuse a machine with no Java 21+; nothing downloads.
- There is no release-signing key, no `cosign`/`sigstore` step, and no published public key.

## Decision 1 — where the digests come from

| Option | What it means | Cost |
| --- | --- | --- |
| **A. Compile host digests into `oq`** | A generated source file lists `(platform, url, sha256)` for the pinned LTS, regenerated per release | Digests in the tree, regenerated by a script, verified by a consistency test |
| **B. Compile a publisher key, verify a signed manifest at install** | `oq` holds a public key; a signed manifest fetched at install names the digests | Needs a signing key and a manifest host; the manifest is itself a network dependency, so D8's offline story needs a cached copy |
| **C. Trust the vendor's own signature** | Verify the JDK vendor's signature (e.g. an OS package signature) instead of a digest | Ties `oq` to one vendor's tooling and platform behaviour; not portable across the three supported platforms |

Option A is the smallest thing that satisfies D3's wording and needs no new infrastructure
beyond a generation step. Option B is stronger — it rotates without a release — and is what the
signing item implies. Option C is least work and least portable.

## Decision 2 — the pinned runtime

ADR-0048's open question names a single pinned LTS per `oq` release as the default and
user-selectable LTS as deferred. **D2 supports five platform combinations** (Linux x86_64 and
aarch64, macOS x86_64 and aarch64, Windows x86_64), so a single pinned LTS means five archives,
five digests, and five upgrade paths per release. The count is five rather than six because
Windows on aarch64 is not in `PlatformSupport.SUPPORTED`, which lists exactly what ADR-0048 D2
names; this brief said six until it was checked against the code.

## Decision 3 — the vendor

D3's wording is vendor-neutral, and no choice here is technically forced. The relevant axis is
whether the vendor publishes a stable, machine-readable digest per archive. This brief did not
recommend a vendor; naming one is a packaging commitment the maintainer has to make.

## Outcome — resolved as Option A with Eclipse Temurin

The brief was written before the decision was taken, and is retained as the record of the options
rather than as an open question. The chosen answer is **Option A**: digests compiled into the jar,
for **Eclipse Temurin `jdk-21.0.13+9`**. The reasoning, in the order it mattered:

1. **Option A needs no new infrastructure and no key ceremony.** D3 asks that a downloaded archive
   be proven to be the one `oq` intends; a digest literal in the artifact does that for a network
   attacker and for a substituted mirror. Option B (signing a manifest) protects the same thing
   but depends on the signing key's custody, and a key that has to be handled on every release is
   a larger operational commitment than the threat it closes here.
2. **A compiled digest is strictly harder to attack than a digest file beside the archive.** The
   literal has to be changed in a source release and re-signed by the release process, so an
   attacker who controls the mirror has nothing to overwrite.
3. **Temurin publishes a stable per-archive `.sha256.txt`.** Every one of the five archives below
   has a vendor-published digest at a deterministic URL, which is what makes the compiled table
   auditable rather than merely plausible.

The pinned artefacts, all cross-checked against the vendor's own digest files:

| Platform | Archive | Bytes |
| --- | --- | --- |
| linux/x86_64 | `OpenJDK21U-jdk_x64_linux_hotspot_21.0.13_9.tar.gz` | 207,858,352 |
| linux/aarch64 | `OpenJDK21U-jdk_aarch64_linux_hotspot_21.0.13_9.tar.gz` | 205,995,218 |
| macos/x86_64 | `OpenJDK21U-jdk_x64_mac_hotspot_21.0.13_9.tar.gz` | 193,957,782 |
| macos/aarch64 | `OpenJDK21U-jdk_aarch64_mac_hotspot_21.0.13_9.tar.gz` | 199,754,598 |
| windows/x86_64 | `OpenJDK21U-jdk_x64_windows_hotspot_21.0.13_9.zip` | 205,421,281 |

One consequence of that table is worth recording because it was not obvious from the ADR: only
Windows is a ZIP. The other four are tarballs, and Temurin publishes no ZIP for Linux or macOS, so
D4's extractor had to learn tar for D3 to be usable at all. That was discovered by running the
install against the real release, not by reading the ADR.

## What this replaced

The brief's proposal was to ship `RuntimeProvenance` against an empty digest map, so that the
*absence* of a digest was a refusal rather than an accident, and leave the data to be filled in.
That was not done, because an empty map refuses every archive and makes the install path
untestable end to end. The table above is populated instead, and the negative property the empty
map would have given is preserved: an archive for a platform not in the table is refused, and
`RuntimeProvenanceTest` asserts that the pinned table and `PlatformSupport`'s supported list name
exactly the same set, so adding a platform to one without a digest for it fails the build.
